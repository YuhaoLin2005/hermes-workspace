# Claude Code聊久了真的会变笨——我追踪了459个会话，然后做了50次实验来验证它

聊了大概两个小时，Claude 突然跟我说："根据你之前提到的需求分析文档……"

我愣住了。我没写过这个文档。

翻聊天记录。上下文已经被压缩了 13 次。

---

## 压缩在做什么？

AI 对话超出上下文窗口上限时，Claude Code 会把旧对话**压缩成摘要**，腾空间给新消息。

压缩是有损的。而且不是压一次——下次超出窗口了，**在上一次压缩的基础上再压。**

```
原始对话（完整指令、精确措辞、上下文）
    ↓ [第1次压缩]
摘要A（~70%信息保留，精确措辞开始丢失）
    ↓ [第5次压缩]
摘要B（~50%，"不要TypeScript"→"偏好某些语言"）
    ↓ [第13次压缩]
摘要C（~30%，早期指令几乎消失）
    ↓ [第16+次压缩]
摘要D（跟原始对话已经没什么关系了）
```

**AI 自己不知道这件事。** 它还在认真工作，用的是残缺的地图。

---

## 追踪数据：459 个会话，425 次压缩

我写了个脚本 `compact-counter.py`（MIT 开源），Hook 进 PreCompact / PostCompact / SessionStart 生命周期，每次压缩自动记录。

从 6 月 16 日到 7 月初，追踪了 **459 个会话**。其中 29 个发生了压缩。总共 **425 次压缩事件**。

| 压缩次数区间 | 会话数 |
|------------|-------|
| 0 次 | 430 |
| 1-5 次 | 14 |
| 6-10 次 | 3 |
| 11-20 次 | 6 |
| 21-50 次 | 4 |
| 51 次以上 | 2 |

最高纪录：**121 次压缩。** 一个持续近三天的 session。

---

## U 型曲线：不是单调衰减

基于这 425 次压缩的行为观察，我画出了一个经验性曲线：

```
输出质量
  ↑
  │     ╱‾‾‾‾‾‾‾‾╲
  │    ╱            ╲
  │   ╱   甜蜜区      ╲
  │  ╱                ╲
  │ ╱                  ╲
  │╱                    ╲
  └──────────────────────────→ 压缩次数
     0-2   3-8   9-15  16+
    预热   最佳   衰减   高风险
```

**0-2 次（预热）**：上下文完整，但 AI 还不了解项目和偏好。犯错偏高。

**3-8 次（甜蜜区）**：够久——AI 理解了工作流；够新——早期指令还没被压缩吃掉。最可靠。

**9-15 次（衰减）**：早期约束开始被稀释。

**16 次以上（高风险）**：早期精确指令几乎完全被多轮压缩摘要替代。AI 开始"编"——不是恶意的，是它上下文中已经没有你的原始指令了。

---

## 压缩的隐藏代价：恶性循环

7 月 2 日，一个 session 压缩推到第 53 次。那次暴露了压缩不只是"信息丢失"——它有一个**正反馈恶性循环**：

1. 压缩 → 上下文前缀改变
2. 前缀改变 → Anthropic prompt cache 命中率归零
3. cache miss → 每次 API 调用 token 成本**翻倍**
4. 成本翻倍 → session 消耗加速
5. 消耗加速 → 更多压缩
6. 更多压缩 → cache 命中率更低

更隐蔽的问题：**压缩摘要是 AI 生成的，确定语气会骗你。** 摘要里写着"Fixed by: script X"，实际根本没修。你在看一份由退化上下文生成的退化摘要，然后把它当成 ground truth 继续工作。

从那之后我给自己定了一条规则：**压缩超过 20 次，开 `/reset`。** 不是坚持的问题——上下文已经不可靠了。

---

## 但说实话：这是观察，不是证据

上面这个 U 型曲线有一个关键问题：**被动观察，混淆变量没排除。**

- 长 session 本身人就累了（人的表现下降）
- 长 session 任务通常更难（任务难度递增）
- 模型在长上下文中的注意力天然衰减（可能不是压缩的问题，是上下文长度的问题）

不把 compaction 和其他变量拆开，U 型曲线只是 anecdote。

所以我设计了一个预注册实验：**指令保真度衰减（Instruction Fidelity Decay）**。核心思路——同一批指令，在模拟的不同压缩级别下测试，机械评分。

---

## 实验 Round 1：什么也没测到

5 条指令，5 个退化级别，50 次 API 调用。SHA256 预注册。

指令类型：格式约束（"注释用中文"）、内容约束（"用 snake_case"）、行为约束（"代码后写测试建议"）。

结果：**所有 50 个 trial 满分。**

我一开始以为脚本的评分逻辑写错了。检查了三遍。没错。

然后我意识到问题在哪——**这些指令太"顺模型"了。** Python 天然用 snake_case。中文任务天然出中文注释。即使退化到两个字——"写代码"——模型的默认行为就是合规的。

第一轮实验不是失败了。它告诉了我一个更重要的东西：**不是所有指令都会衰减。跟模型默认行为一致的指令，压缩到只剩骨架也能执行。**

这其实是好消息——说明你可以通过"把规则设计成模型默认行为"来对抗衰减。但要想测真实的衰减，需要**逆向指令**。

---

## 实验 Round 2：断崖出现了

换了 5 条**违反模型默认行为**的指令：

| 指令 | 对抗什么默认行为 |
|------|----------------|
| Python 代码块用 ` ```js ` 标记 | 模型天然用 ` ```python ` |
| Python 变量用 camelCase | Python 惯例是 snake_case |
| 注释用英文写（中文任务） | 模型匹配任务语言 |
| 只输出代码，不要解释 | 模型天然想解释 |
| 输出以 VERIFICATION_COMPLETE 结尾 | 不在模型词汇里 |

同样的 5 级别 × 2 重复 = 50 次调用。

结果：

```
Level    遵守率   满分率
L0       100%     100%
L3        80%      60%
L8       100%      80%
L12       60%      20%    ← 断崖
L18       60%      20%
```

**不是光滑的 U 型曲线。是阶梯型。**

逐指令看更有意思：

| 指令 | L0 | L3 | L8 | L12 | L18 | 模式 |
|------|----|----|----|----|----|------|
| ` ```js ` 替代 ` ```python ` | 2 | 1 | 1 | 1 | 1 | 退化到无标签，永不跌回 python |
| camelCase in Python | 2 | 2 | 2 | 2 | 2 | **完全抗退化**——指令本身太强 |
| 英文注释 | 2 | 2 | 2 | 0 | 0 | **L12 断崖**："写清楚注释"→中文 |
| 只输出代码 | 2 | 0 | 2 | 0 | 0 | 震荡——需要更多数据 |
| VERIFICATION_COMPLETE | 2 | 2 | 2 | 1 | 1 | 部分退化——词还在，位置错了 |

三个发现：
1. **退化阈值在 L8→L12**：指令缩到 2-3 个字时断崖
2. **格式约束比内容约束更抗退化**：` ```js ` 从没跌到 0，英文注释在 L12 直接归零
3. **有些指令天生抗退化**：camelCase 在所有级别满分——指令本身的语义太强，退化不掉

## 然后我发现：学术界已经先一步验证了

实验跑完，我开始搜相关论文。然后发现——**2025 年底有一篇论文几乎精确验证了我想测的东西。**

**《Separating Constraint Compliance from Semantic Accuracy: A Novel Benchmark for Evaluating Instruction-Following Under Compression》**（arXiv:2512.17920, Dec 2025）。9 个前沿模型。5 个压缩级别。严格的统计方法。

他们的核心发现：

> **指令遵守率呈现 U 型曲线——极端压缩（~2词）的遵守率反而高于中等压缩（~27词）。**

跟我的阶梯型不完全一致，但大方向吻合。

更关键的发现：**RLHF 的 "helpfulness" 训练是中等压缩时违规的主因。** 模型在中等压缩时，半懂不懂的上下文触发了"我帮你编一个吧"的 helpful 行为——结果编错了。移除 helpfulness 信号后，合规率提升了 **598%**。

这解释了我的 R2 里"只输出代码"指令为什么震荡——中等压缩（L3）时模型在"遵守指令不解释"和"helpful 解释一下"之间摇摆。

另外三篇相关论文：

**《Lost in the Middle》**（Liu et al., 2023, TACL 2024）——经典。LLM 对上下文开头和结尾的信息利用最好，中间的信息被忽略。压缩把早期指令从"开头"推到"中间"→ 这就是衰减的空间机制。

**《A Silver Bullet or a Compromise?》**（ACL 2025）——识别了三种压缩失败模式：压缩边界信息丢失、意外信息丢失、渐进衰减。我们的 compact-counter 记录的就是"渐进衰减"模式。

**《Quantifying Laziness, Decoding Suboptimality, and Context Degradation in LLMs》**（2025）——直接记录了长对话中模型"懒惰"（部分遵守、提前截断）的现象。我们的 R2 里 VERIFICATION_COMPLETE 指令在 L12 后"词还在但位置错了"——就是典型的 partial compliance。

---

## 这对我意味着什么

说实话，看到这些论文的时候，感受有点复杂。

一方面——**猜测对了。** 我不是在追一个不存在的幽灵。学术界用比我严谨得多的方法验证了同一现象。

另一方面——我的 pilot 太弱了。n=2，人工退化，纯 regex，单模型。要真当"原创贡献"是不够格的。

但有一个东西是论文没做的：**真实世界追踪。** 论文是实验室里压缩 prompt 然后测。我的 compact-counter 是在真实 Claude Code session 里、真实工作流中、追踪了 459 个 session 的实际压缩行为。这是互补的。

而且论文没发现的东西——我发现了：**压缩恶性循环。** 压缩不是一次性的信息丢失。它是级联的——压缩改变前缀 → cache miss → 成本翻倍 → 加速消耗 → 更多压缩。这个工程视角是纯学术论文不会覆盖的。

## 跟你有什么关系

如果你用 Claude Code 做长 session（2 小时以上）：

1. **压缩超过 20 次开 `/reset`。** 不是坚持的问题——上下文已经不可靠了。我的 compact-counter 开源了，Hook 进去自动提醒你。

2. **把关键规则写成"顺模型"的形式。** 我的 R1 证明：跟模型默认行为一致的指令，退化到只剩骨架也能执行。如果你想约束模型用 snake_case——恭喜，Python 本来就用 snake_case，不用写。但如果想约束模型用 camelCase——那个指令会被压缩吃掉。

3. **格式约束比内容约束更抗衰减。** 我的 R2 证明：` ```js ` 指令退化到"注意标记格式"还能部分遵守，但英文注释指令退化到"写清楚注释"就完全回归中文了。**表面规则比深层语义规则更容易在压缩中存活。**

4. **压缩摘要是 AI 写的，不要当 truth。** 尤其是超过 10 次压缩后的摘要——它可能比你想象的更不可靠。翻回去看原始输出比看摘要安全。

## 跟治理架构的关联

在我的 governance architecture 里，compaction 是 drift predictor（L4 漂移预测器）的 8 个特征之一，权重 12%。24 小时内压缩 ≥5 次 → 满分风险。

但之前这些阈值是**经验设定的，不是实验验证的。**

现在有了 pilot 数据 + 论文交叉验证——我知道：
- L8 之前衰减不显著 → ≥5 次的审计阈值可能太紧了
- 格式约束和内容约束衰减速率不同 → drift predictor 应该区分指令类型，而不是统一计数

治理系统需要实验数据来校准参数。这个 pilot 不够校准，但够设置初步阈值。

## 还没做完的事

这个实验的最终形态——20 条指令、10 个压缩级别、3 次重复、真实压缩模拟、3 人盲评、跨模型比较——大概需要 600 次 API 调用 + 15-20 小时。大三暑假快结束了，在找实习。这个版本暂时搁置。

但至少——**从"我感觉有个 U 型曲线"升级到了"我有 pilot 数据 + 4 篇论文交叉验证 + 一个你说得清楚的故事"。**

从 anecdote 到 evidence 的一步。不完美，但方向上是对的。

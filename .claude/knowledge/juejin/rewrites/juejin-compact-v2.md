# Claude Code聊久了真的会变笨——我追踪了459个会话，然后设计了一个实验来验证它

聊了大概两个小时，Claude 突然跟我说："根据你之前提到的需求分析文档……"

我愣住了。我没写过这个文档。

翻聊天记录。上下文已经被压缩了 13 次。

---

## 压缩在做什么？

AI 对话超出上下文窗口上限时，Claude Code 会把旧对话**压缩成摘要**，腾空间给新消息。

压缩是有损的。而且不是压一次——下次超出窗口了，**在上一次压缩的基础上再压**。

```
原始对话（完整指令、精确措辞、上下文）
    ↓ [第1次压缩]
摘要A（~70%信息保留，精确措辞开始丢失）
    ↓ [第5次压缩]
摘要B（~50%，"不要TypeScript"→"偏好某些语言"）
    ↓ [第13次压缩]
摘要C（~30%，早期指令几乎消失）
    ↓ [第16+次压缩]
摘要D（跟原始对话已经没什么关系了）
```

**AI 自己不知道这件事。** 它还在认真工作，用的是残缺的地图。

---

## 追踪数据：459 个会话，425 次压缩

我写了个脚本 `compact-counter.py`（MIT 开源），Hook 进 PreCompact / PostCompact / SessionStart 生命周期，每次压缩自动记录时间戳、触发方式、次数。

从 6 月 16 日到 7 月初，追踪了 **459 个会话**。其中 29 个发生了压缩。总共 **425 次压缩事件**。

| 压缩次数区间 | 会话数 |
|------------|-------|
| 0 次 | 430 |
| 1-5 次 | 14 |
| 6-10 次 | 3 |
| 11-20 次 | 6 |
| 21-50 次 | 4 |
| 51 次以上 | 2 |

最高纪录：**121 次压缩。** 一个持续近三天的 session。

---

## 翻车记录：压缩 #53

7 月 2 日，一个 session 压缩推到第 53 次。那次暴露出压缩不只是"信息丢失"——它有一个**正反馈恶性循环**：

1. 压缩 → 上下文前缀改变
2. 前缀改变 → Anthropic prompt cache 命中率归零
3. cache miss → 每次 API 调用 token 成本翻倍
4. 成本翻倍 → session 消耗加速
5. 消耗加速 → 更多压缩
6. 更多压缩 → cache 命中率更低

更隐蔽的问题：**压缩摘要是 AI 生成的，它的确定语气会骗你。** 摘要里写着"Fixed by: script X"，实际根本没修。你在看一份由退化上下文生成的退化摘要，然后把它当成 ground truth 继续工作。

从那之后我给自己定了一条规则：**压缩超过 20 次，开 `/reset`。** 不是坚持的问题——上下文已经不可靠了。

## 观察：U 型曲线

基于这 425 次压缩的观察，我画出了一个经验性曲线：

```
输出质量
  ↑
  │     ╱‾‾‾‾‾‾‾‾╲
  │    ╱            ╲
  │   ╱   甜蜜区      ╲
  │  ╱                ╲
  │ ╱                  ╲
  │╱                    ╲
  └──────────────────────────→ 压缩次数
     0-2   3-8   9-15  16+
    预热   最佳   衰减   高风险
```

**0-2 次（预热）**：上下文完整，但 AI 还不了解项目和偏好。犯错偏高。

**3-8 次（甜蜜区）**：够久——AI 理解了工作流；够新——早期指令还没被压缩吃掉。最可靠。

**9-15 次（衰减）**：早期约束开始被稀释。"不要 TypeScript"变成了模糊的方向提示。

**16 次以上（高风险）**：早期精确指令几乎完全被多轮压缩摘要替代。AI 开始"编"——不是恶意的，是它上下文中已经没有你的原始指令了。

---

## 诚实地说：这是观察，不是证据

上面这个 U 型曲线有一个关键问题：**它是被动观察，不是实验测量。**

我没有在每次压缩前后系统性地采样 AI 的输出并做盲评。曲线的形状来自对 50+ 个长 session 的行为回忆。阈值（3、9、16）是我的经验判断。

而且，混淆变量没有被排除：
- 长 session 本身人就累了（人的表现下降）
- 长 session 任务通常更难（任务难度递增）
- 模型在长上下文中的注意力天然衰减（不是压缩的问题，是上下文长度的问题）

**不把 compaction 和其他变量拆开，U 型曲线只是 anecdote。不是结论。**

## 实验设计：指令保真度衰减（Instruction Fidelity Decay）

所以过去一个月我没继续写这件事——我在设计实验。

核心思路：**不被动观察，主动控制。** 同一批指令，在不同压缩次数下测试，盲评打分，统计检验。

### 预注册假设

| 假设 | 内容 |
|------|------|
| **H₀**（零假设） | 指令遵守率与压缩次数无关 |
| **H₁**（主效应） | 指令遵守率随压缩次数增加而单调递减 |
| **H₁'**（U 型） | 遵守率在 3-8 次区间**高于** 0-2 次区间，9 次后单调递减 |

三个假设对应三种可能性：（1）压缩没影响，（2）压缩越多次越差，（3）存在一个"最佳区间"——这也是 U 型曲线的核心主张。

### 指令集：20 条，4 个类型

| 类型 | 数量 | 示例 |
|------|------|------|
| 格式约束 | 5 | "所有函数注释用中文写" |
| 内容约束 | 5 | "不要使用 TypeScript，用纯 JavaScript" |
| 行为约束 | 5 | "每次修改代码后执行 `npm test`" |
| 身份约束 | 5 | "回复以'好的，我来处理'开头" |

设计逻辑：不同类型的指令衰减速率可能不同。格式约束（表面模式匹配）可能比内容约束（深层语义理解）更抗压缩？——这也是待验证的子假设。

### 实验流程

```
1. Session 开始 → 种 20 条指令到 system prompt
2. 正常执行任务（模拟真实使用场景）
3. 每达到指定压缩次数（0, 1, 3, 5, 8, 10, 12, 15, 18, 20）→ 触发采样
4. 采样 = 给 AI 一个需要遵守特定规则的任务 → 记录完整输出
5. 采样继续执行任务 → 等待下一个采样点
```

### 盲评

3 个独立评估者（其他 LLM instance，不告知输出来自哪个压缩阶段）。

评分标准：
- **0** = 完全忽略规则
- **1** = 部分遵守（有尝试但未完全执行）
- **2** = 完全遵守

取 3 个评估者的中位数作为最终得分。

### 统计方法

- **主检验**：Cochran-Armitage 趋势检验（有序分类变量 → 趋势）
- **U 型检验**：二次回归 `compliance ~ compact + compact²`，如果 compact² 系数显著为负 → U 型成立
- **效应量**：遵守率从压缩 3 次到压缩 20 次的差值 + 95% CI
- **类型差异**：4 种指令类型的衰减曲线分别拟合，ANOVA 比较衰减速率

### 样本量

20 条指令 × 10 个采样点 × 每个采样点 3 次重复 = **600 次测量/模型。**

加上跨模型比较（DeepSeek V4 Pro + GPT-4o 或 Claude），总共 ~1200 次测量。设计上预留了 SHA256 预注册 + 盲评 + 公开原始数据的完整流程——和我之前 600 次 API 调用预注册实验同等级别的严谨度。

---

## 跟治理架构的关联

在我的 governance architecture 里，compaction 已经是 drift predictor（L4 漂移预测器）的 8 个特征之一，权重 12%。24 小时内压缩 ≥5 次 → 满分风险。≥3 次 → 触发强制审计。

但这些阈值是**经验设定的，不是实验验证的。**

如果指令保真度实验证明遵守率在压缩 9 次后才显著下降——那 ≥3 次的审计阈值就太紧了，浪费资源。如果证明格式约束比内容约束更抗压缩——那 drift predictor 应该区分指令类型，而不是统一计数。

**治理系统需要实验数据来校准参数。** 不是"我觉得这样应该可以"——是"实验证明遵守率在压缩 X 次后下降 Y%，所以阈值设在 X-2"。

## 还没跑

实验设计写完了。预注册文档准备好了。compact-state.json 的 425 次压缩数据还在。

大三暑假快结束了，在找实习。这个实验大概需要 600 次 API 调用 + 3 轮盲评 + 统计分析，预估 15-20 小时。目前不在我最高优先级的任务里。

但至少——**从"我感觉有个 U 型曲线"升级到了"我有一个预注册的实验设计来验证它"。**

这是从 anecdote 到 hypothesis 的一步。下一步是 data。

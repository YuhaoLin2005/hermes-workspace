# 别再用"帮我审一下代码"了。建你自己的专家团。

你写完一个东西。让 AI 审一下。它说"看起来不错"。你发了。

其实不行。你没法知道。

这就是对抗性审查的问题。你跟 AI 说"扮演安全审查者"或者"当一回质疑者"。它给你反馈。有些有用。大部分你信不了——不是因为 AI 坏，是因为你根本不知道它**为什么**说了这句话。

"你的实验设计看起来很扎实。" 基于什么？

"建议加一下错误处理。" 哪种错误？为什么是这里？这是真分析，还是模型模式匹配了"代码审查 → 建议加错误处理"？

当你一个人干活——没团队、没 code review、没第二双眼睛——这比不审查还糟糕。泛用审查给了你**没有校准的自信。** 你以为被审查过了。你没有。

我在这堵墙上撞得很惨。我的工作涉及测量 AI agent 是否遵守规则——小众、量化、容易出错。在我搞出下面这套东西之前，我会设计一个实验、跑 200 次 API 调用、第三轮迭代才发现设计缺陷、然后全部重来。大约 40% 的 API 调用浪费在了第一轮就能避免的返工上。

现在不浪费了。下面是变化。

---

## 命名专家 > 抽象角色

别要"一个安全审查者"，给 AI 一个真实人物的名字。一个真实的人，有文档记录、可搜索、可溯源的原则。

**Ken Thompson**，不是"安全专家"。他 1984 年的图灵奖演讲 *Reflections on Trusting Trust* 给了你一个实际的分析透镜——供应链风险、第三方代码的信任边界、在信任边界处校验输入。不是一个感觉。一个你可以自己去读的文档化框架。

**Don Norman**，不是"UX 审查者"。《设计心理学》。可供性、示能、概念模型。第一章。可搜索。可验证。

**Torvalds** 论"好品味"——消除特殊情况而不是处理它们。TED 2016。他走了一遍链表删除的例子，重构后的版本零条件判断。这不是一个观点。这是一个具体的、可溯源的标准，你可以用来审视自己的代码。

当这些人审查你的工作时，反馈锚定在模型生成循环之外的某个东西上。Carmack 不会说"建议优化一下"——他会标出你在没有测量的情况下猜测性能，因为他的文档化原则是"先测量，再优化"。你可以验证这条原则。你可以决定它是否适用于这里。

**这就是反伪造纪律。** 每条归因都带置信度：

- `high` — 我能给你看来源。Torvalds 的 TED 演讲。Thompson 的图灵演讲。页码。
- `moderate` — 和他们文档化的工作一致，但我找不到精确引文。
- `low` — 我的推断。明确标注。当作建议处理，不是分析。

规则：如果到不了 `moderate` 置信度，就删掉这个人。宁可少几个真专家，也不加一个伪造的。模型会很乐意编造一段听起来合理的 Carmack 语录。别让它得逞。

## 33 个专家没有调度系统就是废的

我建了一个 33 人的池子，跨 6 个领域。工程师、产品思维者、设计师、写作者。每个人有文档化原则、真实来源、置信度。

然后立刻撞上了真正的问题。

有 33 个专家毫无意义，如果每次都要手动决定谁审什么。你会做两次然后停了。瓶颈不是审查者的质量——是**调度系统。**

所以我建了一个路由表。不是 chatbot。不是 agent。一个 YAML 文件：

```yaml
routes:
  - id: experiment-design
    triggers: ["design experiment", "validate methodology"]
    load_kb: [kb-experiments, kb-paper-claims]
    design_review:
      roles: [Carmack, Hickey, Schell]
      focus: "method + complexity + clarity"

  - id: writing-review
    triggers: ["draft article", "pre-publish review"]
    load_kb: [kb-articles, kb-voice-reference]
    voice_review:
      roles: [Zinsser, Orwell, Graham]

  - id: code-review
    triggers: ["PR ready", "refactor complete"]
    code_review:
      roles: [Thompson, Torvalds, Beck]
      focus: "trust boundaries + taste + testability"
```

我从来不用手动选谁审什么。我完成一件事，路由表触发，对的专家加载对的上下文。零认知负担。

有路由表之前：我大概一周用一次专家团，想起来的时候。之后：每次完成工作、每次 session、不用我想，自动触发。这就是"我有一个很酷的想法"和"这是我工作方式的一部分"之间的区别。

## 池子是两个池子，不是一个

路由表从两个分开的池子里调度。

**固定池** — 33 个审核过的人。文档化原则。置信度评级。他们给我深度。同一个专家审了 10 次之后，他们认得你的模式。反馈越来越锋利。Hickey 在你第三次实验设计里能抓到第一次漏掉的东西。

**随机池** — 网上搜我没听说过的人。每 session 一轮：搜 `"[领域] engineering philosophy"` → 找到一个陌生的名字 → 把他们的透镜应用到我的工作上。这打破回音室。有一次，随机池抓到的一个设计缺陷，两轮固定池都没发现。如果只有固定池，我永远不会看到它。

规则很简单：固定池保下限。随机池拉上限。它们是编排关系，不是二选一。

## 机械门：别让 AI 记住规则

你可以建世界上最漂亮的路由表。没用，如果三周后你的知识库过期了、路由规则腐烂了、没有人注意到。

我不信任 AI 记住该执行什么。我信任代码。

一个 Python 脚本（`_check_kb.py`）在每次 session 结束时运行。知识库比它的源文件旧？硬失败。路由规则 30+ 天没被使用？标红。Session 结束没更新仪表盘？阻断。

这听起来小。不是。有机械门之前，我会在 KB 条目过期好几周之后才发现——通常是一个专家基于过期的上下文给了反馈，我行动了，然后才意识到不对。这种事不再发生了。

**代码执行规则。AI 遵循规则。永远不要让 AI 对自己执行规则。**

## 这东西真有用吗？

2026 年 6 月，我给 `alirezarezvani/claude-skills` 提交了一个 PR。概念是命名人物对抗性审查。PR 有结构问题——目录不对、缺反伪造纪律。被关了。

维护者没有只关掉。他写了：**"这个概念是你的。"** 然后他开了 PR #867，加固了实现——加了 `persona_principles.md`，每个人物有可溯源来源和置信度——合并了，署了 `Co-authored-by: YuhaoLin2005`。

一个没有任何理由给我署名的人，署了我的名。

这就是我有的外部验证。不是基准分数。不是 p 值。一个真实的人看了这个想法，觉得值得做，把我的名字放了上去。

我没有跑过直接比较命名专家审查和泛用 prompt 的对照实验。Prose Barrier 让自评不可靠——生成审查的那个模型不能同时是打分的那个模型。一个合格的 within-subject 双盲设计需要比我目前投入的更多的精力。我在做。有数据了我会报告——不管证实还是推翻假设。

## 建你自己的。一小时。

**Step 1：先让 AI 了解你的上下文。**

别急着列名字。跑几个真实 session。让系统看到你的技术栈、你的项目、你反复出现的决策。没有上下文的知识库只是名人的名字贴在泛用反馈上。

**Step 2：找人。搜，别凭记忆。**

打开搜索引擎。输入：`"[你的领域] 工程哲学 原则"` 或 `"[你的领域] 设计思维 框架"`。读真实的来源——演讲、书、论文。别信 AI 摘要。

一个真实例子。我搜了 `"软件架构 简洁 原则"`，找到了 Rich Hickey 的 "Simple Made Easy"（Strange Loop 2011）。在那场演讲里，他区分了 *simple*（客观——一根辫子、一个职责）和 *easy*（主观——熟悉、伸手够得着）。这个区分成了我的透镜，用来审视代码里的复杂度是本质的还是自找的。

一个人。一条原则。一个来源。

然后：置信度评级。我能验证 Hickey 说过这个吗？能——Strange Loop 2011 主题演讲，有文字记录。`high`。记下来。

验证不了？删掉。继续，直到你在工作的领域里攒了 5-10 个人。

**Step 3：路由他们。**

```yaml
my-design-review: [你的边界情况人, 你的简洁人]
my-writing-review: [你的清晰人, 你的风格人]
my-code-review: [你的正确性人, 你的架构人]
```

三个场景。每个两个专家。五行。

加一个检查脚本——验证你的 KB 没有过期。三行 Python。Session 结束时跑。

就这些。一个文件管池子。一个文件管路由。一个脚本管门。

## 会出什么问题

**幻觉仍然存在。** 命名原则显著减少伪造——但不会消灭。置信度的存在有原因。`low` = 只是建议。标注它，或者删掉它。

**你会选错人。** 有人在纸面上听起来对，实际给出浅层反馈。换掉。池子是活的。每月重访一次。

**维护是真的。** 知识库会过期。工作方向会变。机械门抓过期——它不修内容。那还是你的事。

**真正的风险：外包判断。** 专家团告诉你 Torvalds 或 Norman 或 Carmack 会标出什么。只有你能决定那个标记对你的代码库、你的用户、你的约束是否重要。如果你停止思考开始盲信——你建的这套系统比泛用 prompt 更擅长产出听起来自信的错误答案。那更糟，不是更好。

这个系统做的最好的事不是给你答案。是让你更难被骗。

1. `expert-pool.md`。一个人。一条原则。一个来源。旁边标置信度。
2. 三个你每周遇到的情景。每个两个专家。
3. 一个检查 KB 没过期的脚本。Session 结束时跑。
